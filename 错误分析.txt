【2026-09-15】动态 Skill YAML 配置把未加引号的 on/off 解析为布尔值
错误要点总结：新增 `skill_mode: on | off | auto` 后，YAML 解析回归测试发现未加引号的 `on` 被 PyYAML 按 YAML 1.1 规则读取为 `True`，导致工作流报“skill_mode must be one of auto, on, off”。这会让用户按自然 YAML 写法启用或关闭 Skill 时无法启动 Run。
关键证据：`skill_mode: on` 进入解析器时的值为 Python `True`；同样规则下 `off` 会变为 `False`。
根因分析：解析器只接受字符串，没有兼容 YAML 1.1 对 on/off 的历史布尔语义。
解决步骤：1. 在 Workflow DSL 的 `skill_mode` 解析函数中显式把布尔值 `True/False` 映射为 `on/off`；2. 字符串仍严格限制为 `auto/on/off`；3. 增加 YAML alias、默认值、自动选择、手动开启和关闭的回归测试。
验证结果：后端完整测试 92 项通过；前端 TypeScript 检查与生产构建通过；本地 Skill Registry 已加载 7 个内置 Skill。

【2026-09-15】审查成果包 `run_c1535a368d-artifacts` 发现前后端均不可直接运行
错误要点总结：用户下载的学生管理系统成果包只有根目录平铺文件，前端入口、Vue 单文件结构、依赖和后端 Java 包目录没有形成可构建工程；页面存在白屏或 404，CRUD 链路无法验证。
关键证据：`index.html` 引用 `/src/main.js`，但成果包没有 `src/main.js`；`App.vue` 只有 `<template>` 和 `<style>`，没有 `<script setup>`，且模板之后混入两套未包裹脚本；`api.js` 引入 `axios`，但 `package.json` 没有 axios；Maven 工程没有 `src/main/java` 与 `src/main/resources`，因此 `mvn compile` 返回成功只是因为没有找到源码，并未编译 Java 文件。

验证结果：在原成果包中执行 `npm run build` 失败，Vite 报无法解析 `/src/main.js`；未把该成果包判定为可运行交付物。
补充检查：使用 UTF-8 直接读取源码后，`<title>` 实际内容为 `ѧ������ϵͳ`，不是正常的“学生管理系统”，说明生成内容还存在一次字符编码损坏，修复工程结构后必须重新生成或统一恢复 UTF-8 文本。

根因分析：项目从旧 DAG Runtime 演进到 LangGraph Runtime 时保留了被覆盖的旧入口；后续功能持续直接加入 Executor，缺少清晰的应用层门面和领域服务边界。测试主要验证业务结果，没有约束重复方法、直接 Provider 调用和文件体积，导致结构退化长期未被发现。
实际解决步骤：1. 删除旧的重复 `_run_state`，只保留 LangGraph 状态执行入口。2. 将 `RunState` 移到独立状态模块。3. 抽离 `ModelInvocationService`、`RuntimePolicyResolver`、`FailureFactRecorder`、`WorkspaceArtifactCollector`、`ArtifactDeliveryService` 和 `ArchitectureContractService`。4. 将 Architecture 的合同预检、有界回退、错误指纹熔断、Blueprint 冻结从 Executor 移入架构合同服务，Executor 仅编排调用。5. 保留兼容门面，避免现有 API 和测试导入失效。6. 新增结构守卫测试：禁止重复方法、禁止 Executor 直接调用 Provider、限制主文件行数，防止职责重新膨胀。7. 在 `agent.md` 写入模块边界约束。
修复过程发现的回归：首次抽离架构服务后，测试对 Executor 模块内 `build_delivery_contract` 的替换不再生效，导致“合同构建失败必须阻止审批”用例失真。根因是服务直接静态导入构建器，绕过原有注入点。已改为构造函数注入 `contract_builder` 与 `blueprint_builder`，并让修复回调继续通过 Executor 兼容入口进入，既保持模块边界也保留可测试性。
验证结果：Executor 从 3741 行降至 3157 行，方法数从 63 降至 53，重复方法为 0；架构修复、审批依赖、端到端和结构专项测试 71 项通过；后端全量测试 688 项通过、0 失败、1 项按环境跳过；前端 TypeScript 检查与 Vite 生产构建通过。当前剩余风险是 `_execute_step` 仍约 1045 行，Artifact 验证/候选修复编排仍应作为下一阶段独立服务继续拆分，但本次未用高风险重写替换已通过的恢复链路。

【2026-09-21】Docker Engine 未运行导致快捷启动器整体终止
错误要点：双击 `启动开发环境.bat` 时，本地 6379 端口没有 Redis；Docker CLI 虽已安装，但 Docker Desktop Linux Engine 的命名管道不存在。旧启动器直接执行 `docker compose up` 并将非零退出码视为致命错误，因此 API、Worker 和前端都未启动。
根因分析：项目后端已经支持 `redis` 与 `local` 两种执行模式，SQLite 也能持久化 Run 和 LangGraph Checkpoint，但快捷启动器只实现了 Redis 强依赖路径，没有检查 Docker Engine 状态、尝试启动 Docker Desktop，也没有调用既有 local 模式作为有界降级。另一个隐患是 local 模式仍会仅因环境中存在 `REDIS_URL` 而构造 Redis Coordinator，可能继续访问不可用 Redis。
实际解决步骤：1. 启动器先探测 Redis TCP，再探测 Docker Engine；Engine 离线时自动查找并隐藏启动 Docker Desktop，最多等待 45 秒。2. Docker 或 Redis 仍不可用时，仅本次进程切换为 `AGENT_TEAM_EXECUTION_MODE=local` 并清除继承的 `REDIS_URL`，不改写 `.env.runtime`。3. local 模式下后端不再构造 Redis Coordinator，继续使用独立 SQLite Checkpoint 恢复 Run。4. 提供 `AGENT_TEAM_REDIS_REQUIRED=1` 严格开关，生产或 Redis 专项验证时仍可禁止降级。5. 启动日志明确说明降级后保留的持久化能力以及暂时关闭的多 Worker、跨进程事件和租约功能。6. README 增加两种启动路径和严格模式说明，并增加启动器回归测试。
验证结果：PowerShell 脚本语法通过；修正后的快捷启动流程实际完成 Redis、API、Worker 和前端启动；健康接口返回 `status=ok`、`executionMode=redis`、Redis 可用且 1 个 Worker 在线；前端返回 HTTP 200；Docker Redis 容器状态 healthy。启动器/Redis/平台专项测试 18 项通过、0 失败、1 项按环境跳过；后端全量测试 690 项通过、0 失败、1 项按环境跳过。

【2026-09-21】* browser-render/browser-crud 超时被错误归责给 Frontend
错误要点：糖果广告网站 Run `run_6b4791aaf5` 的 Backend 节点显示成功但实际生成 0 个后端文件，Tester 在浏览器新增记录后等待 `crud-row` 中的随机名称超时，候选验证进一步显示 `/api/candies=HTTP 404`。旧失败分类只看到检查目标为 frontend，因此反复要求 Frontend 修复，不能建立后端接口。
根因分析：Architecture 返回了描述型技术栈 `Spring Boot + Spring Data JPA + H2` 和 `HTML/CSS/JavaScript，static/index.html，同源 REST`。交付合同没有将它们规范化为平台内部枚举 `springboot` 与 `html`，导致 Blueprint 使用普通 Python 后端的 Ownership，ContractCompiler 不能产生 Spring Boot 文件 DAG；Backend Agent 收到空文件计划后仍被标记成功。验证器随后按静态页面运行，真实 REST 地址自然返回 404。浏览器超时是下游症状，不是单纯的前端刷新问题，也不是模型强度或 Token 不足。
实际解决步骤：1. 在合同冻结层增加 Backend/Frontend 技术栈规范化，兼容模型返回的描述性名称。2. `DeliveryContract` 自身加入字段规范化，确保其他入口也只能向下游提供稳定枚举。3. ContractCompiler 为 Python 后端补齐确定性文件 DAG，并在 Architecture 冻结前检查所有必需 Agent 必须拥有非空 `file_plan`；空计划直接回退 Architecture，不再生成“0 文件成功”。4. Spring Boot + HTML 现在确定生成 `pom.xml`、Application、Entity、Repository、Service、Controller、application.yml，以及 `src/main/resources/static` 下的前端文件。5. FailureClassifier 识别浏览器日志中的 `/api/...=HTTP 404/405/5xx`，同时归责 Backend 与 Frontend，允许联合修复接口实现、路径和代理，而不是只改表单。6. 增加描述型技术栈、Blueprint Ownership、文件计划和浏览器 API 404 责任路由回归测试。
验证结果：合同、Blueprint、Artifact、Architecture 和 Repair 专项测试通过；后端全量测试 693 项通过、0 失败、1 项按环境跳过。历史失败 Run 使用的是已经冻结的错误合同，不应只重试 Tester；需要从原始需求创建新 Run，或显式从 Architecture 重新生成合同。

【2026-09-22】* 全链路失败分流仍有盲区，恢复能力扩展后 Executor 再次膨胀
错误要点：成果物验证后的文件修复已经较成熟，但架构合同、冻结合同、Provider/环境、最终交付压缩包和旧版 FailureFact 的处理口径不统一；部分失败会重试错误 Agent，最终交付缺证据时直接结束，历史 Run 也可能因失败记录字段不同而无法恢复。连续增加恢复逻辑后， WorkflowExecutor 又增长到 3904 行并突破结构守卫。
根因分析：失败事实缺少统一兼容入口，Retry 仍部分依赖节点状态和错误字符串；Architecture、交付门禁和普通成果物修复各自维护回退逻辑；候选修复缺少足够严格的文件证据、原子提交和责任边界；新增功能继续直接写入 Executor，导致已拆分的调度门面重新承担恢复细节。全量回归还发现：自定义主要实体留空时提示过于泛化，以及冻结合同已损坏时，旧目标推断仍可能把 Backend 暴露成下游修复目标。
实际解决步骤：
1. 扩展 Architecture 合同错误分类与有界回边；冻结后的合同缺陷可重新打开、要求再次审批，并使下游成果物与旧验证证据失效。错误指纹重复且无推进时熔断，不能绕过 entity_id 等约束。
2. Retry 统一读取 FailureFact 决定恢复边界；旧格式失败记录在读取时规范化并保留证据。平台、验证器、环境和 Provider 配置错误不会再盲目改业务代码。
3. Candidate Workspace 使用结构化文件操作、全包原子提交和 Owner/Ownership 校验；优先使用验证器证据与编译器精确路径定位文件。缺少类、方法、构造器或类型不匹配时允许在同一候选中逐步推进编译 Gate，无推进或破坏已通过 Gate 才撤回。
4. 跨层 API 与数据库失败支持多责任 Agent；Backend 合同已通过时只修 Frontend。责任 Agent 重放不得修改冻结合同或其他 Owner 文件。
5. 浏览器验证持久化截图、DOM、Console、Network、表单值和 CRUD 状态；最终交付门禁可有界回修，ZIP 损坏或清单不一致由平台重新物化、打包和复验，不派给代码生成 Agent。
6. 需求确认改为 Schema 驱动，展示平台推荐、参考提示和用户自定义输入；自定义管理对象为空时给出明确提示并拒绝继续。
7. 取消流程先持久化取消意图，等待底层任务结束后再写 STOPPED；重复停止保持幂等。运行统计覆盖失败位置、责任方、修复轮次、目标 Gate、完整回归、自动修复率、熔断、耗时和 Token。
8. 将重试/合同重开/失效清理抽到 run_recovery.py，将证据定位/Owner 重放保护/修复候选选择抽到 artifact_repair_support.py；WorkflowExecutor 从 3904 行降到 2909 行，恢复为编排门面。
9. 新增企业恢复矩阵，覆盖静态 HTML、localStorage、Spring Boot + HTML、Vue + Spring Boot、双实体 CRUD，以及故意注入的漏 entity_id、漏文件、错误路由和验证器内部故障；所有失败必须保持 Gate=failed，禁止改成 skipped 伪造通过。
验证结果：定向恢复、Artifact、责任路由、需求确认与结构守卫测试 111 项通过；企业恢复矩阵 12 项通过；后端全量测试 737 项通过、0 失败、1 项按环境跳过；前端 TypeScript 检查和 Vite 生产构建通过。真实云端模型输出质量与第三方服务波动仍需通过实际 Run 持续观察，但失败将保留证据、有限回退并可恢复，不再无限循环或静默改错 Agent。
