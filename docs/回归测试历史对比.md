# Agent-Team 历史回归测试对比

整理日期：2026-09-25

范围：项目已有的 L1–L10 编码 Agent 难度递增回归测试，以及此前的阶段性测试记录。

## 结论摘要

最可比的两轮完整 L1–L10 测试，交付率从 **0/10（0%）提升到 9/10（90%）**，提高 **90 个百分点**；首轮交付率从 **0/10 提升到 6/10（60%）**。最新一轮 10 个场景全部完成运行，9 个通过交付门禁，L4 未通过。

这说明当前版本在这组测试上的交付表现明显改善，但还不能据此断言对所有用户需求都有 90% 的稳定成功率：两轮的工作流版本不同，历史报告也没有记录 Provider/模型，且目前只有各一轮完整测试。

## 这轮通过率提高的可能原因与技术

下面区分“测试和工作流快照能直接证明的变化”与“合理但尚不能单独证明因果的解释”。

### 有直接证据支持的变化

1. **从整段代码循环生成切换为按文件生成 Artifact。** 9 月 24 日快照中，Database、Backend、Frontend 使用 `coding_loop`；9 月 25 日改为 `artifacts`。Artifact 模式先得到文件清单，再针对文件分别请求模型，文件间独立生成；已有文件不会因某个文件失败而整体重做，可对当前文件执行恢复。这降低单个超长响应被截断、整批源码随重试丢失的风险。实现见 `backend/app/workflow/artifact_generation.py`。
2. **明确数据库到后端的依赖顺序。** 新快照中 Backend 显式依赖 Database，生成后端时可以读取先生成的数据库成果物；比只依赖架构审批更容易保持表结构、实体和接口实现一致。Frontend 与 Database 仍可并行准备，保留了一定并发。
3. **交付以验证证据为准，而不是 Agent 自报完成。** 冻结的交付合同把技术栈、实体、API 和文件范围作为验收依据；验证器检查真实成果物，并可启动 Spring Boot、执行 Maven 检查、通过 H2 API 进行 CRUD 往返验证，以及在浏览器中检查页面与交互。所有 9 个通过项都满足交付门禁。
4. **失败后做有边界的定点修复。** 最新一轮 L5、L8、L9 各经历 1 次修复后通过，其余 6 个成功案例首轮通过。候选工作区、文件归属和目标检查用于隔离修改并避免把未验证修复直接当作交付；相关实现分布在 `artifact_repair_support.py`、`delivery_gate.py`、`workspace.py` 等模块。

### 对结果的解释

- 本轮 **6/10 首轮通过 + 3/10 修复后通过 = 9/10 最终可交付**。修复路径确实挽回了 3 个失败案例；按文件拆分和明确的 Backend/Database 顺序，是另外值得关注的工作流变化。
- L4 被 `delivery-api:POST:/api/convert` 门禁拦截，说明门禁要求 API 实现与冻结合同有明确验证证据。它没有把缺证据的成果物误报为成功；目前报告不足以据此断定接口代码本身有缺陷。
- 虽然项目已实现 SWE 风格的工具调用编码循环和隔离工作区，但本次统计记录为 **3 次循环、0 个工具动作、0 个编码循环修复候选**。因此不能把这次 9/10 的提升归功于 Agent 自主调用代码工具；本轮主要验证到的是 Artifact 生成和验证修复路径。
- Token 预算评估并不是两轮之间新增的能力：两份快照都已有 Requirement 后的 Token Estimator。它可能影响预算安排，但不能单独解释本次通过率变化。
- LangGraph/YAML 编排也不是这两轮之间的新变量；这次可见的流程变化主要是生成模式、节点依赖和文件级生成/恢复策略。

### 已使用的关键技术

| 技术 | 在项目中的用途 |
|---|---|
| YAML DAG + LangGraph | 声明 Agent 节点、依赖和审批，由统一执行器调度；本轮后端生成依赖数据库成果物。 |
| Artifact Manifest / 文件级生成 | 先规划文件，再按文件独立生成、检查和恢复，缩小单次输出与修复范围。 |
| Frozen Delivery Contract | 冻结实体、字段、技术栈、API 路径及交付范围，协调多 Agent 的共享接口。 |
| 确定性 Gate + 真实集成验证 | 组合文件/合同检查、Maven、服务启动、H2 CRUD 和浏览器交互证据，决定是否可交付。 |
| 有界修复 + Candidate Workspace | 根据失败证据定点修改隔离候选，先验证目标，再确认是否可晋级；避免无限循环或污染已通过结果。 |

### 归因限制

这是一组真实运行的前后对比，不是受控实验。除工作流 SHA 已变化外，报告没有记录 Provider、模型、模型参数或服务端状态；因此只能说上述变化与通过率提升同时出现，**不能证明某一项单独造成了全部 90 个百分点的提升**。同时本轮耗时增加 26.1%，说明验证和修复路径带来了额外执行时间，当前改善主要体现在交付可靠性和 Token 总量，而不是端到端速度。

## 最新未通过项

L4 单位转换器因交付门禁 `delivery-api:POST:/api/convert` 未通过：系统没有找到足以证明该 POST API 与冻结合同中的方法、字段一致的明确验证证据。现有报告能证明“验收证据不足”，但不能仅据此断定页面或接口实现本身错误。后续应补上该路由的实际请求/响应验证，并让验证报告关联到合同字段，而不是放宽 Gate。

## 可比性与统计限制

- 两次完整轮次使用相同的 10 个场景 ID；9 个场景的冻结需求哈希完全一致。L3 的 9 月 24 日失败记录没有生成交付合同，因此缺少旧需求哈希，无法从报告 JSON 做哈希核验。
- 工作流版本不同：9 月 24 日为 `373bfeb587eeb43dc47c0058f7d0e5e2a619152e61e93083db5921a87b65e9ea`；9 月 25 日为 `2ac7c2b7e547f6c1bcfaf83545571d67f1c9c2599207bd44d828cc8c361f21c6`。因此这是版本前后对照，不是固定环境下的受控 A/B 实验。
- 两份报告都标记为 `live`，但没有保存 Provider 和模型名，无法排除模型、服务状态或采样随机性带来的影响。
- 每个完整批次目前都只有一次，90% 是本批次实测值，不是长期成功率估计。要验证稳定性，建议固定用例、Provider/模型、工作流版本和运行参数，重复完整批次，并记录环境元数据。
- “首轮可交付”按报告定义统计；最新轮的 3 个非首轮通过案例各发生 1 次验证修复。Gate 通过以验证证据为准，不以 Agent 自报完成为准。
