# Coding Agent 交付率提升方案

目标是让代码 Agent 在受控工作区内「生成 → 验证 → 据证修复」，同时保留 LangGraph 编排、冻结的外部 API/数据库合同和最终独立验收；不以关闭 Gate 换取绿灯。

1. **受控验证入口**：Agent 只选择平台定义的构建/测试档位，不能传任意命令、路径或超时；验证结果回到同一编码循环，失败证据用于定点修复。最终 Tester 仍须独立验收。
2. **逐文件恢复**：每个完整文件生成后保存 Run 快照；相同需求及合同下重试时跳过已有文件，只补失败文件。合同重开则清除旧检查点。半成品不进入正式成果物清单。
3. **早期验证**：完成一个责任 Agent 的文件后，优先跑该责任方的快检，再进入跨端集成；错误按归属和文件证据回传，修复轮次有上限。
4. **合同边界**：外部 API、字段、数据表冻结；内部辅助文件可在归属范围内由证据驱动新增，但必须记录原因、重新验证，不得悄悄修改对外合同。
5. **验收与度量**：从已确认需求形成可执行 Gate，区分「文件存在」「构建通过」「真实页面/API 可用」；记录首次通过率、自动修复率、耗时与 Token，避免只凭 Agent 自述交付。

## 本次落地状态

- 已落地 1：`verify.run` 只能选择责任方授权的固定档位；Backend 可编译，数据库分支独立时不提前运行可能误判的 Backend 测试；Frontend 只接受冻结的 `vite build`，依赖缺失时仅按冻结白名单安装，拒绝任意命令、路径及非 registry 版本。构建直接调用工作区内 Vite CLI，避免 `npm run` 顺带执行 `prebuild/postbuild`。验证失败的真实输出回到 Coding Loop；源码变更后允许重验同一档位。最终 Tester 不受此工具结果替代。
- 已落地 2：生成文件逐个保存 Run 快照。失败重试仅在需求及编译合同指纹相同时复用已完成文件，定点恢复指定文件时强制重新生成目标；合同重开清除旧进度。正式成果物仍等责任 Agent 完成后才登记。
- 已落地 3：Backend、Frontend、Database 生成完成后先做责任方结构预检；根据证据在隔离候选区限一次修复，预检未推进则撤回候选。此预检只检查结构，不声称构建、启动或联调通过。
- 降低固定开销：Spring Boot `Application.java`、Vue `index.html` 和 `src/main.js` 由冻结技术栈确定性生成，业务文件继续按需求与合同生成。
- 已落地 4 的新增审计：冻结计划外、但仍属于 Owner 的辅助文件，在 `fs.create` 前必须提交 8–240 字的 `reason`；原因随动作意图和工具审计记录保留。越权文件仍被拒绝；新增文件并不豁免后续合同及交付 Gate。
- 5 的现有基础：冻结 API/实体/表合同、Owner 文件归属、DeliveryContract/DeliveryGate、浏览器及 API/H2 Gate、Run 级修复/Token/耗时指标已存在。本次没有重写这些模块，也没有关闭任何 Gate。

## 仍需验证和补强

1. 在真实 Provider 上重跑 L1–L3，比较首次成功、最终交付、耗时与 Token；单元/模拟测试不能证明实际生成成功率提升。
2. 当前计划修订只记录新增辅助文件的原因；仍需把修订明确关联到触发它的编译/验证证据，并在前端展示。外部 API/DB 合同不得随内部文件调整而变化。
3. 将用户确认的验收意图编译为独立、可执行的 AcceptanceSpec，并映射到现有 DeliveryGate；不能把模型建议的额外能力误当用户必需项。
4. 当前 LocalSandbox 只是本地进程边界，Maven/POM 和 npm 依赖仍可能执行不可信代码；公开接收不可信仓库前，必须迁到限制网络、CPU、内存和文件访问的强隔离 Worker。
